# Database Design - Openned (MongoDB)

We chose MongoDB because the schema of a "Developer Knowledge Graph" (skills, various integrations, varying project metadata) is inherently polymorphic and evolves rapidly.

## 1. Global Schema Standards
All documents across all collections will adhere to the following standards:
*   **Audit Fields**: `createdBy` (ObjectId), `updatedBy` (ObjectId).
*   **Timestamps**: `createdAt` (Date), `updatedAt` (Date). (Mongoose handles this automatically).
*   **Soft Delete**: `deletedAt` (Date | null), `isDeleted` (Boolean). Queries will globally filter out `isDeleted: true`.

## 2. Collections & Relationships

### A. Users
Central authentication and profile data.
*   `_id`: ObjectId
*   `clerkId`: String (Unique, Indexed) - Maps to auth provider.
*   `email`: String (Unique, Indexed)
*   `name`: String
*   `subscriptionTier`: Enum ('FREE', 'PRO', 'ENTERPRISE')

### B. KnowledgeGraphs (One-to-One with User)
The core intelligence hub for the developer.
*   `userId`: ObjectId (Indexed, Ref: 'Users')
*   `skills`: Array of Objects
    *   `name`: String (e.g., "React")
    *   `verifiedVia`: Enum ('GITHUB', 'LEETCODE', 'MANUAL')
    *   `proficiencyScore`: Number (0-100 calculated by AI)
*   `technologies`: Array of Strings

### C. Integrations (One-to-Many with User)
Stores OAuth tokens and metadata for connected platforms.
*   `userId`: ObjectId (Ref: 'Users')
*   `provider`: Enum ('GITHUB', 'LINKEDIN', 'LEETCODE')
*   `accessToken`: String (Encrypted at rest using KMS/Vault)
*   `refreshToken`: String (Encrypted)
*   `metadata`: Mixed (Store provider-specific IDs like github_username)
*   *Index*: Compound index on `{ userId: 1, provider: 1 }` (Unique).

### D. Projects (One-to-Many with User)
Analyzed repositories and personal projects.
*   `userId`: ObjectId (Ref: 'Users')
*   `integrationId`: ObjectId (Ref: 'Integrations', Optional)
*   `title`: String
*   `description`: String
*   `url`: String
*   `metrics`: Object (stars, forks, linesOfCode)
*   `aiSummary`: String (Generated by GitHub Analyzer)
*   `architectureTags`: Array of Strings (e.g., ["Microservices", "Event-Driven"])

### E. Resumes (One-to-Many with User)
Generated resumes tailored for specific jobs.
*   `userId`: ObjectId (Ref: 'Users')
*   `targetJobId`: ObjectId (Ref: 'Jobs', Optional)
*   `content`: JSON (Structured representation of the resume)
*   `atsScore`: Number
*   `pdfUrl`: String (Link to S3/GCS bucket)

### F. JobApplications (One-to-Many with User)
The Kanban board data.
*   `userId`: ObjectId (Ref: 'Users')
*   `companyName`: String
*   `role`: String
*   `status`: Enum ('BOOKMARKED', 'APPLIED', 'INTERVIEWING', 'OFFER', 'REJECTED')
*   `appliedDate`: Date
*   `jobDescription`: String
*   `resumeUsed`: ObjectId (Ref: 'Resumes')

### G. Communications (One-to-Many with JobApplications)
Emails parsed by the Email Engine.
*   `applicationId`: ObjectId (Ref: 'JobApplications')
*   `messageId`: String (Unique)
*   `type`: Enum ('INBOUND', 'OUTBOUND')
*   `aiIntent`: Enum ('REJECTION', 'INTERVIEW_INVITE', 'OFFER', 'UNKNOWN')
*   `contentSummary`: String (AI generated summary)

## 3. Indexes & Performance
*   **Single Field Indexes**: `userId` is indexed on every collection where it exists to support fast multitenant lookups.
*   **Compound Indexes**: 
    *   `JobApplications`: `{ userId: 1, status: 1, appliedDate: -1 }` (for sorting the dashboard).
*   **Text Indexes**: On `Projects.title`, `Projects.description` for fast searching within a user's portfolio.

## 4. Security Considerations
*   **Encryption at Rest**: MongoDB Atlas encryption at rest.
*   **Field Level Encryption**: OAuth tokens in the `Integrations` collection MUST be encrypted before saving to the DB using a symmetric key manager.
*   **Validation**: Strict Mongoose schema validation / JSON Schema validation at the DB level to prevent NoSQL injection and malformed AI outputs.

## 5. Future Scalability (Sharding)
As the platform grows, the `KnowledgeGraphs` and `Projects` collections will become massive. 
*   **Shard Key**: `{ userId: 1 }`. This ensures all data for a specific developer resides on the same shard, making reads extremely fast since our query patterns are almost exclusively tenant-isolated.
